Understanding MCP

What Model Context Protocol actually is, why it exists, and how to connect one, in plain English.

With Dr. Erin Jacques · Join the Leveraging AI community →

Start with an analogy.

Imagine hiring the smartest employee you've ever met. But every time they need to use Gmail, Slack, your CRM, or your database, you have to hand them a completely different instruction manual. And every time you add a new tool, you have to teach them all over again.

That sounds ridiculous, but that's essentially how we've been building AI applications.

MCP is the fix for that. It's why powerful AI integrations are suddenly more accessible than ever.

First, what's an API?

An API is one piece of software asking another to do something.

For decades, APIs have been the backbone of modern software. Check the weather, book a flight, log in with Google, an API is working behind the scenes. One app sends a request, another processes it and sends back an answer. Fast, predictable, reliable.

But for that to work, the first app has to already know three things:

EndpointWhere to send the request ParametersWhat information to include ResponseWhat answer to expect back

The weather-app example.

Say you're building a weather app. The endpoint is like a department inside the weather company, it tells the server which thing you want:

api.weathercompany.com/current

But that's not enough, it needs to know which city. That extra info is a parameter:

api.weathercompany.com/current?city=Miami

And the server sends back a response (usually as JSON, a structured way to organize data):

{ "city": "Miami", "temp": "86", "sky": "sunny" }

The catch: the software already knew all the rules before it ever sent the request.

So why isn't that enough for AI?

Because traditional software follows instructions. AI reasons.

Your weather app already knows the endpoint, the parameters, and the response, because a developer programmed all of it ahead of time. An AI model doesn't have that advantage.

Ask it "what's the weather in Miami today?" and it understands your question, but it doesn't automatically know which endpoint has today's weather, which parameters that endpoint expects, or what the response will look like. All it starts with is your intent.

Traditional software

Given the exact steps to follow.

AI

Starts with a goal, and has to figure out which tool to use and how.

That gap is exactly why MCP was created.

What MCP actually is

A middleman that lets the app describe itself.

An MCP server sits between an AI model and an application. Its job is to advertise what the application can do, in a standardized format the AI understands.

Think of it as a table of contents for the application.

Instead of forcing the AI to guess what's available, the MCP server tells it: here are the capabilities I offer, here's what each one does, here's the information I need from you, and here's what I'll return. It does that using structured descriptions called JSON schemas.

So instead of a developer manually teaching the AI how to use every endpoint, the application does the job of describing itself.

How it flows, start to finish.

You ask a large language model (Claude, ChatGPT, Gemini) to do something.
The AI reads the capabilities the MCP server advertises.
It picks the one that best matches your request.
The MCP server uses the application's existing APIs to actually do the task.
The result comes back, and the AI turns it into a plain-language answer for you.

The APIs didn't change. The app didn't change. What changed is the AI no longer has to be manually taught, the application advertises what it can do.

Does this replace APIs?

No. MCP works with APIs, it sits on top of them.

Most of the time, your existing APIs are still doing the real work behind the scenes: retrieving data, updating databases, sending emails, creating tickets. What changed is who knows how to use them.

Before MCP, developers had to manually teach the AI how to talk to every API. With MCP, the application advertises its own capabilities and the AI discovers and uses them on its own.

It's not MCP versus APIs. It's MCP working with APIs. APIs stay the foundation; MCP just makes them easy for AI to understand and use.

Why it matters

Every major shift lowers the barrier to building.

Creating a website once meant writing HTML by hand. Then website builders opened it to millions more people. Then no-code tools. Now it's happening with AI.

MCP doesn't eliminate developers, it dramatically reduces the custom work needed to connect AI to the tools you use every day. That means powerful AI workflows aren't just for big companies with engineering teams, but for solopreneurs, creators, small businesses, anyone with an idea.

The question is shifting from "can I build this?" to "what do I want to build?"

How to connect an MCP
Here's the practical part, connecting an MCP in Claude Code. We'll use Supabase (a database) as the example, but the flow is the same for any MCP.

1 Point Claude at the MCP

An MCP starts with a small config file in your project, .mcp.json. It simply tells Claude where the MCP server lives (its address) and which project it's for. Claude Code can create this file for you, just ask it to set up the Supabase MCP for your project.

👉 This file is the "address." It doesn't connect you yet, it just tells Claude where to knock.

2 Open Claude Code and run /mcp

In your terminal, open Claude Code and type /mcp. This is the command that actually connects, it reads your .mcp.json and starts the handshake.

3 Authorize it

Pick the server (Supabase) and approve it. Most MCPs use a secure sign-in (OAuth), so a browser window opens and you click authorize. That one-time approval is what gives Claude permission to use it.

👉 Do this in the terminal Claude Code, not the side panel, the connection lives in the session where you ran /mcp.

4 Just ask

That's it. Claude can now see the capabilities the MCP advertises and use them on its own. You don't hand it endpoints or parameters, you describe what you want:

🗣️ "Create a table for my clients and their progress" — and Claude does it, right in your Supabase database, through the MCP.
🎉 That's the whole idea. You didn't teach Claude how the database works. The MCP advertised what it could do, and Claude figured out the rest. That's the shift.
